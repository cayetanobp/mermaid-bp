# Compilación y publicación

## Antes de integrar cambios

El flujo `Comprobaciones` se ejecuta en cada PR y en `main`. Comprueba web, seguridad, escritorio y contenido legal del instalador NSIS. Los trabajos de CI generan una clave updater efímera por ejecución con `scripts/prepare-ci-updater-key.mjs`; los E2E usan su clave pública en la configuración temporal. Ningún trabajo de CI usa la clave de producción. Las compilaciones Rust pasan `--locked`. Una actualización de `Cargo.lock` debe incluir las features de producción `tauri/custom-protocol` y `tauri/protocol-asset` y actualizar `THIRD_PARTY_RUST_NOTICES.md`; el artefacto del flujo `Generar avisos Rust para revisión` incluye ambos archivos resueltos para `x86_64-pc-windows-msvc`. `node scripts/check-rust-third-party-notices.mjs` verifica el resultado en Linux. La comprobación corre en Ubuntu porque el inventario incluye dependencias de compilación que Cargo resuelve según el sistema anfitrión; el trabajo Windows comprueba los archivos realmente empaquetados.

## Auditoría local de Windows con Docker

En Windows, con Docker Desktop y Node instalados, ejecuta `./scripts/audit-windows-docker.ps1` desde PowerShell. Antes de compilar, exige 30 GB libres en la unidad del checkout (ajustable con `-MinimumFreeGB`) y registra los volúmenes Docker y las salidas del target en `%LOCALAPPDATA%/mermaid-bp/build-cache/<id>/inventory.json`. El script compila el frontend, prepara una imagen con Rust, cargo-xwin, Tauri CLI y NSIS, comprueba los avisos Rust, genera el ejecutable y el instalador Windows, extrae el NSIS y compara sus cuatro archivos legales con las fuentes. Guarda el instalador en `desktop-app/src-tauri/target/x86_64-pc-windows-msvc/release/bundle/nsis/` y escribe `mermaid-bp.sha256` junto a él. La compilación cruzada no sustituye una prueba interactiva de instalación en Windows.

Para revisar las salidas intermedias que se limpiarían, ejecuta `./scripts/audit-windows-docker.ps1 -CleanupUnused -WhatIf`. La previsualización muestra las rutas candidatas sin borrarlas. Omite `-WhatIf` para borrar únicamente las rutas regenerables registradas por esta copia del repositorio; solo se admiten `release/build`, `release/deps`, `release/incremental` y `release/.fingerprint` del target Windows. Se comprueban los procesos Rust y consumidores Docker activos y se rechaza cualquier ruta regenerable que contenga una salida preservada. Añade `-CleanupDockerVolumes` para incluir sus volúmenes etiquetados como propios; antes de borrarlos se vuelve a verificar la etiqueta de propiedad y se rechaza el borrado si un contenedor, incluso detenido, los referencia. Los volúmenes preexistentes sin la etiqueta de propiedad se registran como prestados y nunca se borran. La limpieza se niega si detecta procesos `cargo` o `rustc` activos, o un contenedor en ejecución que monte la ruta de salida. El instalador, su hash y las rutas preservadas quedan fuera de la limpieza. No se ejecutan `docker system prune`, `cargo clean` ni limpiezas globales.

En Linux, `./scripts/build-linux-deb-docker.ps1` aplica la misma precomprobación (25 GB por omisión), registra el paquete Debian como preservado y los volúmenes de Cargo como reutilizables. Usa `-CleanupUnused -WhatIf` para previsualizar; incluye `-CleanupDockerVolumes` cuando quieras eliminar las cachés Docker de propiedad confirmada que no tengan consumidores.

## Publicación beta

Desde `main`, la ejecución manual de `Aplicación de escritorio Windows` compila y verifica el instalador con la clave del entorno protegido `release-signing`; Tauri 2 produce el updater como instalador NSIS `*-setup.exe` y firma `*-setup.exe.sig`. La ejecución de `Aplicación de escritorio Linux` compila, instala y prueba el paquete Debian usando una clave CI efímera. Cuando se ejecuta manualmente desde `main` sin reutilizar una compilación previa, el job `linux-production` usa el entorno `release-signing` para generar los artefactos de publicación. Ambos flujos dejan artefactos privados de Actions; revisa sus resultados antes de publicar. Ejecuta manualmente `Publicar beta` desde `main` con los IDs de ambas ejecuciones y la confirmación exacta `PUBLICAR`. El flujo exige que la compilación Windows manual y el job Linux de producción de una ejecución `workflow_dispatch` hayan concluido correctamente en el HEAD actual de `main`; comprueba la versión web y de escritorio, genera SHA256 y manifiesto para Windows y Linux y adjunta los artefactos a la release versionada.

Las issues abiertas no bloquean por sí solas una release beta: algunas describen coordinación o trabajo posterior a la beta. La autorización explícita `PUBLICAR` y las dos compilaciones verificadas son la barrera de release. El tag de versión no puede existir ya. El alias mutable `beta` se crea si no hay tag ni release; si ya existe, el flujo solo lo actualiza cuando es una prerelease con nombre `Canal beta de Mermaid BP` y su único asset es `latest.json`. Los tags huérfanos, releases estables y assets adicionales detienen la publicación.

El plugin BookStack se publica aparte desde `cayetanobp/mermaid-bp-plugins`, en `main`, después de que `Plugin CI` pase en el mismo SHA, el core sea público y su release beta ya exista. Ejecuta `Publicar plugin BookStack compatible` con la versión beta del core y `PUBLICAR`. El workflow crea `bookstack-v1.0.0.zip`, su SHA256 y un manifiesto de compatibilidad API v1. Si el core sigue privado o no existe la beta, la consulta anónima falla y detiene la publicación. Si ya existe la release, solo acepta un reintento cuando el título y los tres assets coinciden byte a byte; no reemplaza tags ni contenido remoto distinto. La release del core enlaza a ese paquete y el manifiesto del plugin enlaza a la beta del core.
